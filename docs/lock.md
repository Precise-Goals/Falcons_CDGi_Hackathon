The Internet After the API Help software survive undocumented changes in external services THE PROBLEM Modern software relies on APIs, SDKs, MCP servers, webhooks, and third-party services. If a dependency changes behaviour, disappears, becomes rate-limited, or returns subtly different data, applications can silently fail. THE CHALLENGE Build a system that observes external dependencies, learns their real behaviour, detects meaningful changes, assesses which parts of an application are affected, and automatically adapts—or proposes a safe migration. SYSTEM PIPELINE External service  Observed behaviour  Contract / behavioural model  Change detection  Impact analysis  Adapter or migration  Validation  Updated system. EXAMPLE: A SEMANTIC CHANGE An endpoint previously returns GET /users → name but now returns GET /users → display_name. The system should identify which workflows depend on name and determine whether mapping the new field preserves the original meaning. CORE REQUIREMENT Do not rely only on documented schemas. Detect behavioural changes too: altered defaults, different error responses, changed pagination, rate limits, or data that remains valid JSON but changes meaning. DEMO REQUIREMENT Provide an application dependent on several simulated external services. Introduce undocumented changes, then demonstrate automatic detection, impact analysis, adaptation, and validation that affected workflows work again. WHAT A STRONG SOLUTION SHOWS Accurate change detection, dependency mapping, semantics-aware compatibility fixes, regression validation, and safe handling when automatic repair is uncertain. CORE CHALLENGE Build infrastructure that allows software to survive changes in systems it does not control.
